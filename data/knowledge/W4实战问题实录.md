# W4 实战问题实录：重试、断点恢复与人工审批的坑

指数退避重试的三个要点：只重试瞬时故障（超时、429 限流、5xx），
永久故障（404、参数错）重试无意义；等待时间翻倍 1s→2s 给服务端喘息窗口；
重试外壳放在公共包装器层，具体工具完全不感知。

悲观初值原则：重试循环里 success 必须初始化为 False，只有真正成功才翻 True。
如果沿用旧代码的 success=True 初值，异常打断流程后会产出"带错误信息的成功回执"
这种自相矛盾的数据——测试用 assert not obs.success 抓住了它。
初始化值定义语义：单次调用可以默认乐观，循环重试必须默认悲观。

断点恢复（Checkpoint）四坑：
1. 函数签名忘了加 checkpointer=None 参数，函数体内却使用了它 → UnboundLocalError；
2. 初始状态里又生成了一次新的 uuid，导致白板里的 run_id 和 thread_id 不同源
   ——快照归属全靠这两个号对上，必须同源；
3. checkpoint 每步之间有序列化边界：plan 和 pending_approval 里的同名任务
   反序列化后是两份独立拷贝，改 pending_approval 的状态不影响 plan 里那份。
   跨节点改共享状态，必须按 id 定位到目标格子里的那份来改；
4. 恢复时出现 Deserializing unregistered type 警告：自定义 Pydantic 类型
   没有注册进 msgpack 白名单，当前只是警告，未来版本会拒绝——
   "今天能用但明天会坏"的警告要记入待办。

interrupt 人工审批的设计原则：高危工具（如 execute_python）不让 executor
直接执行，executor 只登记 pending_approval，路由进 human_gate 闸门节点；
闸门内调用 interrupt() 冻结全图（快照自动存档），CLI 问人后用
Command(resume={"approved": ...}) 回注。y 路径执行工具，n 路径标记失败。

人的否决是终审：用户拒绝高危操作后，评估器必须判定不再重试
（need_replan=false），否则失败任务被重置 pending 会再次触发审批，
形成"反复拿同一个危险操作骚扰人"的循环。真实教训：一次运行里
重规划连续插了三个新计算任务，每个都要人工批准，队列越走越长。

防御机制要跟着节点走：planner 有"校验失败把报错喂回去重试 3 次"的自愈循环，
replanner 也调 LLM 却是裸奔的——LLM 某次把任务 id 输出成数字而非字符串，
Pydantic 拦下后没有重试，直接崩溃。每个调 LLM 产结构化数据的节点都该有同款防御。

相似名字拿错对象事故家族：route_after_eval / route_after_execute 一对孪生
路由函数，给 executor 挂条件边时递错了名字，导致评估器在评估前就被路由读取，
evaluation 还是 None 就崩了。同族还有 plam、task.id、pending_aproval（少个 p）。
土办法：写 state["格子名"] 时不手打，直接从 schemas.py 复制粘贴。

给 LLM 的 prompt 要带工具参数速查表：LLM 会给 search_github 填 keyword
（真名是 query）、给 execute_python 写多行赋值加 print（只支持单个表达式）。
把每个工具的参数名和取值格式逐字写进 prompt，一次教学省十次失败。

PowerShell 引号坑：给 python -c 传代码时，bash 的 \" 转义写法在 PowerShell
里会提前切断字符串。内部一律用单引号，需要引号套引号就用 chr(111)+chr(115)
这种方式拼出来。

测试技巧：给有全局状态的系统（如工具注册表）做测试，用"顶替+恢复"手法——
存下原函数、把假函数顶进已注册的名字（假名字过不了 Literal 白名单）、
finally 里恢复真身。用字典当计数器记录调用次数（闭包里普通变量不能赋值，字典可以）。
